# MCP Went Stateless and Yegge’s Agent Framework Burned Down: Distribution Got Cheap, Generic Got Worthless

**The short version:** On July 28 the Model Context Protocol shipped its biggest revision since launch — the handshake is gone, sessions are gone, and every request is self-describing. Any call can land on any server instance behind a round-robin load balancer with no shared storage. Building and hosting a tool server just got dramatically cheaper.

In the same window, Steve Yegge published a post-mortem on Gas Town, his reusable agent orchestration framework: it “was intended to be reusable, but I only ever wound up using it to build itself,” and a model upgrade killed it outright. And the second-highest post on Hacker News this week — Sean Goedecke’s *LLMs reward expertise* — argued that with everyone prompting the same models, the differentiator is domain knowledge, not prompting technique.

Three stories, one instruction: **the cost of shipping a capability collapsed, the value of generic infrastructure went to zero, and the only durable input left is what you specifically know.**

---

## Key Insights

**The headline judgment:** the bottleneck for a one-person software business has moved. It is no longer *can I build and distribute this* — stateless MCP made a tool server roughly as hard to deploy as a static site, and the SDKs in four languages shipped the same day. The bottleneck is now *do I know something worth encoding*. Yegge’s framework died because it was general-purpose and therefore had nothing to converge on. Goedecke’s argument explains why: the model already contains the generic capability, and extracting it well requires someone who knows what “good” looks like in a specific domain. If your product roadmap is “a better agent framework,” you are building the thing that just proved it can’t hold. If your roadmap is “the twelve non-obvious rules of how invoicing actually works in freight brokerage, wired to a tool an agent can call,” you are building the thing that got cheap to ship and stayed hard to copy.

**Four numbers that should change a decision:**

| Data point | Value | Why it matters |
| --- | --- | --- |
| MCP SDK adoption | ~**500M downloads/month** across Tier 1 SDKs; TypeScript and Python each past **1B total** | This is not an emerging channel to watch. It’s an installed base to ship into now. |
| Stateless deployment cost | **Zero** shared session storage; any request routes to any instance | Your infra bill for a tool server is now a serverless function, not a stateful cluster |
| Agent memory overhead | Zero-Mem cuts memory-operation time by **57.6%** vs the fastest baseline by removing LLM calls from memory entirely | A large slice of “agent cost” is bookkeeping you can delete, not intelligence you must buy |
| Deprecation runway | **12-month minimum** formal window; Roots, Sampling, Logging, HTTP+SSE all deprecated | You can now plan a migration instead of reacting to one — rare in this ecosystem |

## Market Trends

### 1. MCP 2.0 removed the reason tool servers were expensive to run

The 2026-07-28 specification retired the `initialize`/`initialized` exchange and the `Mcp-Session-Id` header. Each request now carries its protocol version, client identity, and capabilities inline in `_meta`. There’s an optional `server/discover` RPC for clients that want capabilities up front, but it isn’t required.

The operational consequence is the whole story. Previously, a remote MCP server meant sticky sessions, shared state between instances, or careful routing to keep a client talking to the same backend machine. Now, in the maintainers’ words, any request can land on any server instance behind a plain round-robin load balancer without shared storage. That is the difference between “I need a hosting architecture” and “I need a serverless function.”

The rest of the release compounds it. Method and tool names travel in `Mcp-Method` and `Mcp-Name` HTTP headers, so a gateway, rate limiter, or WAF can route, authorize, and *meter* on headers without parsing JSON bodies — which is exactly the primitive you need to bill per call. List responses from `tools/list`, `prompts/list`, `resources/list`, and `resources/read` now carry `ttlMs` and `cacheScope`, so clients cache your tool catalog and upstream prompt caches stay stable across reconnects. Multi Round-Trip Requests (MRTR) replace server-initiated elicitation and sampling: when a tool needs a confirmation or a missing parameter mid-call, the server returns `resultType: "input_required"` and the client retries with `inputResponses` attached. No held-open bidirectional stream.

There’s a design note in the spec worth internalizing, because it generalizes beyond MCP: dropping protocol-level sessions doesn’t force your application to be stateless. If you need state across calls, mint an explicit handle from a tool and have the model pass it back as an argument. The maintainers found this works better than state hidden in the transport, because *the model can see the handle and thread it between tools*. State the agent can inspect beats state it can’t.

Simon Willison — who had publicly cooled on MCP through 2025, arguing an agent with a terminal and curl could do most of it — reversed on this release and built three clients and servers in a week. His reasoning is the practical one: giving an agent shell access is risky and requires a strong model to drive it, whereas MCP tools are easier to audit and control and *simple enough that smaller models running on a laptop can drive them reasonably well*. His `mcp-explorer` runs with no install at all via `uvx mcp-explorer list <url>`.

**What this means for a solo builder:** the distribution channel for a narrow capability is now standardized, enormous, cacheable, header-routable, and cheap to serve. The build-and-ship side of the equation is solved. What’s left is knowing what to put in the tool.

### 2. Reusable agent frameworks are structurally fragile — Yegge’s post-mortem

Steve Yegge on Gas Town, his agent orchestration framework: it “was intended to be reusable, but I only ever wound up using it to build itself.” Then the model changed underneath it. Up through Opus 4.6 it worked brilliantly. With 4.7 came what he calls the “just two more things” tic, which “prevented Opus from ever converging on being ready to do real work — it always wanted to fiddle with Gas Town itself.” The tic never went away. The framework, in his words, burned down.

Two distinct failure modes are stacked here, and both are common in indie AI projects.

The first is **meta-work capture**: a general-purpose tool with no specific job attracts infinite improvement to itself. There is always another abstraction to add because nothing external defines “done.” Gas Town’s only real user was Gas Town.

The second is **model-upgrade fragility**: if your product’s value is a thick orchestration layer wrapped around model behavior, a behavioral change in the model — not even a capability regression, just a personality tic — can destroy it. You do not control that release schedule. A framework whose correctness depends on how a specific model version behaves is a business built on someone else’s changelog.

The contrast case in the same conversation is instructive. David Crawshaw’s widely-shared prompt is not a framework at all: *“Set up a nightly cron job that executes the prompt: fetch upstream changes to the software and rebase all local changes on top of upstream. Check that the software works as intended and replace the current version.”* One cron job, one concrete outcome, no abstraction layer. It cannot be captured by meta-work because it has an external definition of success.

**The read:** orchestration should be embedded in a specific business problem, not extracted into a reusable product. When you extract it, you get Gas Town.

### 3. Domain expertise became the measurable input — and the models keep proving it

Goedecke’s argument, at 1,356 points on Hacker News: LLMs make everybody a generalist, so it looks like there’s no skill in using them — everyone is talking to the same model and getting similar results. He says this is wrong, and that the most important skill in prompting is expertise in the domain you’re prompting for.

His evidence is Terence Tao’s public ChatGPT conversation about a counterexample to the Jacobian Conjecture. Goedecke’s observation is that this is visibly not the same ChatGPT he talks to. Tao’s messages are short and to the point. He doesn’t respond point by point, only to the gist. By signalling expertise he shunts the model into talking-to-mathematicians mode rather than explaining-to-amateurs mode. He pushes back without directly contradicting — “this looks more complex than I was hoping for.” And critically, he almost never takes the model’s advice about where to go next.

The part that resists imitation: you cannot prompt like Tao by copying those four habits. The technique *is* understanding the mathematics — pulling the relevant idea out of a multi-paragraph response, proposing alternate formulations, and identifying what looks weird. Goedecke’s own version, at GitHub: with a good theory of your codebase you can push the model much harder, because you can say “no, I think it could be simpler here,” or “but don’t we already do X?”

His conclusion is the one to sit with: **for many tasks the human is the bottleneck, not the model, because the hard part is communicating exactly what kind of solution you want. The information is already in the model; it takes an expert to pull it out.**

A related term made the rounds this week from Niklas Gruhn: **meat proxy** — someone who blindly relays AI output to their peers. The prescription is to read it, understand it, validate it, and then write a response in your own words, which serves as a decent certificate that you did the prior steps. If your product is a thin pass-through of model output to a customer, you have productized being a meat proxy. That’s the category with no defensibility and no pricing power.

### 4. The cheap wins right now are in bookkeeping, not intelligence

A quiet paper worth more than its Hacker News score suggests: **Zero-Mem** (arXiv 2607.29377, submitted July 31). The observation is that many agent memory systems burn additional LLM calls just to *operate* the memory — generating intermediate records and mediating retrieval — which adds recurring token and time cost, and where omitted or merged details can obscure the original evidence.

Zero-Mem asks whether structured memory access requires generation at all, and answers no. No step outside final question answering invokes an LLM or consumes LLM tokens. It preserves original interaction traces as the source of record, organizes them two ways — an entity-context graph for cross-interaction connections, and a temporal hierarchy for conversational locality and session state — weighs both views per query, and only the final reader invokes a model. Result: competitive performance on long-memory and long-context QA benchmarks with a **57.6% reduction in memory-operation time cost** relative to the fastest compared baseline.

Pair this with the tooling shift on the client side. Simon Willison’s LLM 0.32 — the most significant release since launch — added server-side provider tools, so `CodeInterpreter`, `WebSearch`, `WebFetch`, `CodeExecution`, and `AnthropicMCP` execute at the provider rather than in your loop. The new default model for `llm "prompt"` is GPT-5.6 Luna, described as inexpensive but capable. The llm-anthropic 0.26 plugin simplified extended thinking down to `thinking` and `thinking_effort`, and removed `thinking_budget`, `thinking_display`, and `thinking_adaptive` entirely.

**The pattern across both:** in 2026 a meaningful share of agent cost is not intelligence. It’s overhead — memory bookkeeping, orchestration round-trips, context you re-send every turn, knobs nobody tuned. That overhead is being deleted by better architecture rather than cheaper tokens, and it’s deletable by a single person in an afternoon.

## Build Directions

### Direction 1: Ship an expertise-encoded MCP tool, this week

Highest conviction direction this cycle, because both halves just resolved: distribution is standardized and free, and the differentiator is something you already have.

The selection test is a single question: **what do you know that is not on the open web, and that an agent would call repeatedly?** Not “what API can I wrap.” Wrapping a public API is generic — the model can hit it directly. What you want is judgment: the eight edge cases in how a specific industry’s contracts actually get voided; the mapping between a legacy ERP’s field names and reality; which of a regulator’s guidance documents actually supersede each other. Encode the judgment, not the data access.

| Layer | Tool | Cost / notes |
| --- | --- | --- |
| Server | TypeScript or Python Tier 1 SDK, spec 2026-07-28 | Free; stateless means no session store |
| Hosting | Cloudflare Workers / Vercel / Fly.io | Free tier covers validation; round-robin, no sticky sessions |
| State (if needed) | Mint an explicit handle from a tool, model passes it back | Avoid transport-level state — the model can’t see it |
| Metering | Route and meter on `Mcp-Method` / `Mcp-Name` headers at the gateway | No JSON body parsing; works with any WAF or rate limiter |
| Caching | Set `ttlMs` + `cacheScope` on list responses | Cuts your egress and keeps client prompt caches stable |
| Testing | `uvx mcp-explorer list <url>` then `inspect` and `call` | No install |

**Timeline:** 3–7 days if the expertise is already in your head. **Pricing:** per call, cents; or per resolved outcome. **Do this first:** deliberately target smaller models as clients, not just frontier ones. Willison’s point is that MCP tools are simple enough for laptop-scale models to drive — that’s a much larger addressable set of callers than the frontier-model crowd, and far less contested.

### Direction 2: Sell agent memory as infrastructure, not as a framework

Zero-Mem’s result — a 57.6% cut in memory-operation time by removing LLM calls from memory entirely — describes a hole that most teams running agents have and haven’t measured. They’re paying model calls to summarize, merge, and retrieve their own history, and losing evidence fidelity in the process, because merged records obscure the original.

The product is not a memory framework. That’s Gas Town again. The product is a **drop-in memory backend with an honest cost claim**: preserve original traces as the source of record, build the entity graph and temporal hierarchy deterministically, and expose retrieval as one MCP tool call with zero model invocations. The pitch is a number, not an architecture diagram — “your agent’s memory currently costs X per session; this makes it near-zero and stops losing the original evidence.”

| Layer | Tool | Notes |
| --- | --- | --- |
| Store | Postgres + pgvector, or SQLite for single-tenant | Traces are the source of record — never overwrite with summaries |
| Graph view | Entity-context graph over interaction traces | Deterministic construction, no LLM |
| Temporal view | Session hierarchy preserving conversational locality | Deterministic |
| Encoder | Local embedding model | Accounted separately from LLM cost — say so honestly in your pricing |
| Interface | Single MCP tool, stateless | Any agent framework can adopt it without migrating |

**Timeline:** 4–6 weeks to a credible benchmark. **Target customer:** anyone running long-horizon agents where session cost is visible on the bill. **Proof obligation:** publish your own benchmark against a named baseline. This category is full of unfalsifiable claims; a reproducible number is the entire differentiator.

### Direction 3: Verified expert wrappers — sell the validation layer

If “meat proxy” names the failure, the inverse is a business. There are high-stakes domains where AI output is nearly good enough and being wrong is expensive: regulatory filings, clinical documentation, contract review, tax positions, safety certifications. The generic AI tool produces a plausible draft. Nobody in those domains can ship a plausible draft.

The offer is a narrow workflow with a **domain-expert validation step that is a product feature, not a disclaimer** — structured checks encoding what a specialist actually looks for, provenance links from every claim back to source, an explicit confidence and escalation path, and an audit trail. You are selling the certificate that someone competent checked, at software margins for the checkable parts and human margins for the rest.

| Layer | Tool | Notes |
| --- | --- | --- |
| Generation | Any frontier model via LLM 0.32 or direct API | Interchangeable — deliberately don’t couple to one |
| Server-side tools | `WebSearch` / `WebFetch` / `CodeExecution` via provider | Provenance links come free; no scraping infra |
| Validation rules | Your domain checklist as deterministic code | This is the actual product |
| Moderation | Mistral Shieldstral 3B (open weights, fits a 16GB card) | Required if you self-host open models |
| Audit | Full request/response + rule outcomes to Postgres | Compliance artifact and sales collateral |

**Timeline:** 6–10 weeks, most of it spent writing domain rules rather than infrastructure. **Pricing:** per document or per matter, never per seat. **Why it holds:** as models improve, the generation half commoditizes and your validation rules keep their value. The moat compounds in the direction the technology is already moving.

### Direction 4: The nightly-cron category — narrow autonomous maintenance

Crawshaw’s prompt is a template for an underrated product shape: a scheduled agent with one concrete job and an external definition of success. Fetch upstream, rebase local changes, verify it still works, replace the current version. It cannot drift into meta-work because “did the software still work” is decided outside the agent.

Generalize the shape, not the framework: dependency upgrades with verification, config drift detection and correction, docs regenerated from code with a test that the examples still run, translation files kept in sync, data pipelines re-validated after schema changes. Each is a narrow vertical product for one stack.

| Layer | Tool | Cost |
| --- | --- | --- |
| Runner | GitHub Actions, or a $5/mo VPS with cron | $0–5/mo |
| Agent | Minimal harness — four tools and a short system prompt | Avoid heavy frameworks; that’s the Gas Town failure mode |
| Model | Cheap tier by default (GPT-5.6 Luna class); escalate only on failure | Most runs are routine |
| Verification | The customer’s existing test suite | Non-negotiable — this is what prevents meta-work capture |
| Reporting | Diff summary + pass/fail, delivered to Slack or email | Silence on success |

**Timeline:** 2–3 weeks per vertical. **Pricing:** $29–199/mo per repo or per environment. **Design rule:** if you cannot state the external pass/fail condition in one sentence, don’t build it.

## Risk Factors

- **Betting on a spec that just made a breaking change.** The 2026-07-28 revision retired the handshake, deprecated Roots, Sampling, Logging, and the legacy HTTP+SSE transport, and formally deprecated Dynamic Client Registration in favor of Client ID Metadata Documents. There is now a 12-month minimum deprecation window, which is genuinely better than reacting — but it also confirms the surface still moves. Support both the current spec and the prior version at your endpoint for at least a year.
- **Model behavior changes can kill a product without any capability regression.** Gas Town died from a personality tic, not a benchmark drop. If your value sits in an orchestration layer tuned to how one model version behaves, you’re exposed to a changelog you don’t control. Test against at least two model families continuously.
- **Expertise-based moats decay if you stop practicing.** The Goedecke argument cuts both ways: your advantage is that you know a domain, which means it degrades the moment you become a full-time tool builder who no longer does the work. Stay in the domain, or your encoded judgment goes stale.
- **Self-hosted open weights transfer liability to you.** SaferAI’s evaluation found GLM-5.2 refused none of the offensive cyber or dual-use biology tasks it was given, while frontier models refused consistently enough that one benchmark couldn’t complete. Interpol now reports AI involvement in more than half of cybercrime in Africa. If your endpoint gets abused there’s no provider in the chain absorbing it — budget for a moderation layer.
- **Benchmarks are a weakening basis for claims.** A systematic study of benchmark saturation (arXiv 2602.16763) documents the plateau problem, and public test sets leak into training data over time. If your marketing leans on a public score, expect that argument to persuade less every quarter. Build your own task-level evaluation.
- **Compute supply is now a political variable.** Texas has halted new data center approvals pending audits. Cost curves that assume steady regional capacity growth are assumptions, not forecasts — don’t write “inference gets X% cheaper per quarter” into your plan.

## Action Recommendations

**Just starting / solo**

- ✅ Write down the five things you know about your domain that aren’t on the open web. If you can’t fill the list, that’s your real problem — solve it before writing code.
- ✅ Ship one stateless MCP tool this week against spec 2026-07-28. Test it with `uvx mcp-explorer` before writing any client. Target laptop-scale models as callers, not just frontier ones.
- ✅ Audit your current project for meta-work capture: in the last two weeks, did you improve the tool or improve the outcome? If it’s mostly the tool, you’re building Gas Town.
- ✅ Instrument memory cost separately from inference cost for one week. Most people find a surprising share of spend is bookkeeping they could make deterministic.
- ✅ Stop being a meat proxy in your own product. If your output is model text passed to a customer with light formatting, add a validation layer or accept that you have no pricing power.

**Existing product / small team**

- ✅ Add an MCP interface at spec 2026-07-28 this month, and keep the previous version live in parallel. Half a billion SDK downloads a month is a distribution channel, not a science project.
- ✅ Move metering to the gateway using `Mcp-Method` and `Mcp-Name` headers. Per-call billing without body parsing is now a config change, not a project.
- ✅ Set `ttlMs` and `cacheScope` on your list responses. Free egress reduction and it keeps your clients’ prompt caches stable.
- ✅ Replace any transport-hidden session state with explicit handles the model passes between tools. Agent reliability improves when the model can see its own state.
- ✅ Run continuous evaluation against two model families. The Gas Town failure mode is silent until the day it isn’t.
- ✅ Migrate off Dynamic Client Registration toward CIMD now, while the 12-month window is open, not in month eleven.

## What It Means

For two years the reflex when a new AI primitive appeared was to build the layer that makes it easier for everyone to use. That reflex is now backwards. The layer is being standardized underneath you — stateless MCP just did to tool serving what static hosting did to websites — and the frameworks built on the old friction are dying of their own generality. Gas Town’s only customer was Gas Town.

What survives is the opposite shape: narrow, opinionated, externally validated, and loaded with something the model can’t infer from public text. The distribution problem is solved and free. The infrastructure problem is solved and free. What’s left is the part that was never a technology problem — knowing a domain well enough that your judgment is worth calling an endpoint for.

The practical move this week is small and concrete: pick the one thing you know that isn’t on the web, wrap it in a stateless MCP tool, put a price on the call, and let other people’s agents find it. Everything else in this report is a reason that window is open right now.
