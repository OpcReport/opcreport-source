# GitHub Actions Went Dark for Nine Hours — And Half Your Traffic Was Never Human

**August 7, 2026**

Yesterday at 15:22 UTC, GitHub Actions went into a critical incident. It was still in monitoring nine hours later. At the bottom of it, roughly **30–40% of queued jobs were succeeding**, webhook processing was deliberately throttled to about **15%** so the system could drain its own queues, and pushes and pull requests simply stopped triggering workflow runs at all.

It took Actions down. It also took down GitHub Pages, Copilot code review, and — this is the part worth sitting with — **Copilot coding agent**. Enterprise Importer migrations were paused as a precaution. One control plane, one blast radius.

Someone on HN counted: **incident number six for the month of August, on August 6th.**

On the same day, an indie hacker posted an autopsy of a different kind of illusion. His GA4 dashboard showed a modest traffic day. His server was at 90% CPU and about to take the database with it. He SSH’d in, read the raw Nginx logs, and found the traffic wasn’t human — it was scrapers, headless browsers, and AI agents walking every endpoint he had.

Two stories, one shared assumption breaking: **the pipe you build on is reliable, and the traffic you measure is real.** Neither is true by default anymore, and neither is priced into how most one-person companies operate.

---

## Key Insights

- **The outage window was ~8h44m from open to “mitigated”** (15:22 UTC Aug 6 → 00:06 UTC Aug 7), and the incident was still in a monitoring state at 00:59 UTC with Actions Runner Controller runners reported as slow to recover. That is not a blip you wait out — it’s a full working day of not being able to ship.
- **Your coding agent and your CI now fail together.** Copilot coding agent and Copilot code review degraded in the same incident as Actions. If your development loop is “agent writes → CI verifies → deploy,” a single vendor event kills all three steps at once.
- **Agents multiply the number of CI runs, which means outages hurt more than they did last year.** The same pipeline that used to absorb a handful of human pushes a day now absorbs agent-generated branches. Higher run volume against a shared, capacity-constrained queue is exactly the load profile that turns a degradation into a nine-hour queue burn-down.
- **Bots are now the majority of web traffic**, and an AI agent doing a research or shopping task will visit on the order of **1,000x the pages a human visits for the same task.** It doesn’t satisfice. It enumerates.
- **Client-side analytics can’t see any of it.** GA4 loses an estimated **20–30% of real humans** to adblockers and privacy extensions, and is entirely blind to non-JavaScript agents. So the traffic you can’t see is inflating your server bill while the traffic you can see is a partial sample of the wrong population.
- **The agent execution layer is migrating off the laptop.** Hoplite (YC S26) launched cloud coding agents on Modal sandboxes + Temporal durable workflows, and its founders’ stated bet is that developers will review *product output* rather than code while running hundreds of agents concurrently.
- **The best agentic model changed hands again** — Qwen3.8 Max took the #1 overall slot on Artificial Analysis’s agentic index (421 points, 270 comments on HN). Any architecture that hard-codes one provider is opting out of a variable that moves monthly.

## Market Trends

### 1. Your deployment path is a single point of failure, and agents just raised the cost of that

The interesting thing about yesterday’s incident isn’t that GitHub had an outage. It’s the shape of the recovery, which is public in the status updates:

- Job success rates bottomed around 30–40%
- Webhooks throttled to ~15% so queues could drain
- Runners stuck retrying jobs that no longer existed — both hosted *and* self-hosted
- Success climbed to 65%, then 97%, then 99% over roughly five hours of incremental fixes
- Queue burn-down finished around 00:01 UTC, mitigation declared at 00:06 UTC

Read that middle bullet again. **Self-hosted runners were affected too.** The naive resilience answer — “I’ll just run my own runners” — did not fully insulate anyone, because the control plane that assigns jobs was the thing that broke. Isolation only helps if it goes all the way down the stack.

The commercial context makes it worse. GitHub no longer has its own CEO; it’s a Microsoft org. The HN thread is full of enterprise customers saying they get no dedicated resources and no faster path during incidents, and at least one saying support tickets have gone weeks without response. Whatever you’re paying, you’re in the same queue as everyone else.

Here’s the piece specific to this year: **AI agents changed the run volume.** A solo developer with three parallel Claude Code or Codex sessions generates far more branches, far more pushes, and far more CI invocations than the same person did in 2024. You are a heavier consumer of a shared, capacity-limited resource than you used to be, and you probably haven’t re-examined your fallback since you were a light one.

**What this means for you:** the question is no longer “is GitHub reliable enough.” It’s “what is my time-to-deploy when GitHub Actions is unavailable for eight hours, and have I ever tested it.” Most solo builders cannot answer the second half. That’s the exposure.

### 2. Half the internet is machines, and your dashboard is describing a population that doesn’t exist

The indie hacker post is worth reading past the headline because the mechanism matters.

Traditional web architecture, analytics, and cost modeling all assume a request comes from a person in a browser. Three things break at once when that stops being true:

**Cost.** An agent doing comparison research doesn’t stop when it has a good-enough answer. It enumerates. Every page view is CPU, database queries, and bandwidth you pay for, from a visitor that will never convert.

**Measurement.** If your top pages in GA are whatever endpoints crawlers happened to hammer that day, you are making roadmap decisions from noise. And GA’s blind spots run both ways — it under-counts real humans by 20–30% (adblockers) while being fully blind to headless agents, so you can’t even reason about the error bar.

**Defense.** Raw server logs are ground truth and can’t be blocked, but they’re thousands of lines of uncontextualized text. You find the rogue scraper *after* it has already spiked your CPU. Log-based defense is inherently reactive.

There’s an opportunity buried in the complaint. Yes, agent traffic is a cost problem. It is also, increasingly, **a discovery channel** — those agents are answering questions for humans on the other side. An indie product on the front page right now (Orbator) exists specifically to check whether ChatGPT, Claude, and Perplexity recommend you. If half your traffic is machines reading your content on behalf of buyers, the machines are a distribution surface, not just a tax. Almost nobody is designing for that deliberately.

### 3. Agents are moving off the laptop, and the harness question got settled the other way

Two signals in the same week point the same direction.

**Hoplite (YC S26)** launched cloud-deployed coding agents: import your local setup — sessions, memories, MCP servers — and run agents in the cloud with tooling built for QA’ing the *output*. Stack is AWS with Temporal for durable workflows, Modal for sandboxes, PlanetScale for data. Free tier with $100 credits, and you can attach an existing Codex subscription.

**Superconductor** published the argument directly: coding agents belong in remote sandboxes.

Notably, Hoplite’s founders chose to build a **custom harness** rather than wrap Claude Code or Codex — explicitly so they aren’t waiting on Anthropic or OpenAI to ship features. That’s a reversal of the advice that was correct three weeks ago, when four major harnesses went free and the obvious move was “don’t build one.” The nuance: don’t build a harness if you’re building an *application*. Do build one if the harness behavior *is* your product.

Their stated thesis is the one to actually argue with: as models improve, developers review less code and more product output — new user flows, visual verification, does the API respond correctly, does the CLI work on Windows — while running hundreds of agents at once. If that’s right, the tooling gap isn’t code review. **It’s product-level verification at agent scale.** Almost nothing exists there.

### Also worth logging this cycle

- **ChatGPT free users now get unlimited text chats**, plus a “Think” button for Free and Go tiers. The free-tier floor rises again. Anything you charge for that is one model call in a nicer wrapper is being commoditized on a schedule.
- **Microsoft filings suggest ~70% of its AI revenue traces to OpenAI.** Even at that scale, concentration risk is real and unhedged. Your version of this is smaller and identical in shape.
- **OpenAI’s rumored smart speaker is priced at $300–400.** Hardware distribution for assistants is a new lane, and it is closed to you — plan around platform reach, not against it.
- **Qwen3.8 Max is #1 on the agentic index.** Route, don’t marry.

## Build Directions

Five things you can actually start, ordered by time-to-first-version.

### Direction 1 — Deploy-path failover for small teams (the “GitHub is down, ship anyway” product)

|  |  |
| --- | --- |
| **What** | A parallel deploy path that survives a GitHub Actions outage. Mirror the repo, mirror the workflow definition, and give a solo builder a one-command escape hatch that builds and deploys from somewhere else. Recovery time as the product, not features. |
| **Stack** | Forgejo Actions or Woodpecker CI (both consume near-GitHub-Actions syntax) · a Hetzner or Fly.io box for the runner · `git push` mirroring to a second remote · Dagger so the pipeline definition is portable rather than YAML-locked |
| **Cost & timeline** | 2–4 weeks to something you can sell. Infra $20–60/month for the runner tier. Price $15–40/month per repo, or a flat team plan — this is insurance pricing, and it sells for the two weeks after an outage. |
| **Why now** | Six incidents in six days, and the HN thread was full of people saying they’re stuck because Forgejo/Gitea/GitLab aren’t compelling enough to fully migrate to. They don’t want migration. They want a fallback. That’s a smaller product and an easier sale. |

### Direction 2 — Server-log-truth analytics with human/agent separation

|  |  |
| --- | --- |
| **What** | Analytics from access logs instead of a JS beacon, with every request classified: human, known crawler, AI agent, unknown automation. Two dashboards side by side — what you’re paying to serve, and what could actually buy something. |
| **Stack** | Nginx/Caddy log shipping · ClickHouse or DuckDB for storage and query · a small local model (4B–8B is plenty) for user-agent and behavioral classification · optional Cloudflare log push for edge-level truth |
| **Cost & timeline** | 3–6 weeks to MVP. Near-zero marginal inference cost if classification runs locally. Price $9–29/month for indie sites, $99+ for anyone with real traffic. |
| **Why now** | Bots crossed 50% of web traffic and every existing analytics product is still a client-side beacon. The gap isn’t technical — it’s that nobody has packaged the boring log pipeline as a product a non-sysadmin can install in ten minutes. |

### Direction 3 — Make your product legible to agents on purpose

|  |  |
| --- | --- |
| **What** | Not a SaaS to sell — a change to how you build. If agents are 1,000x-ing your page views, stop serving them your full HTML and start serving them a cheap, structured surface: `llms.txt`, a read-only JSON endpoint, an MCP server for your own product. You cut server cost *and* become the source the agent cites. |
| **Stack** | `llms.txt` at root · JSON-LD structured data · a thin MCP server exposing your public data (FastMCP or the official SDKs) · edge cache the agent path aggressively since it’s read-only |
| **Cost & timeline** | 1 week. Basically free. The win shows up as lower infra bills and inbound from AI answers. |
| **Why now** | Products already exist just to check whether ChatGPT/Claude/Perplexity recommend you. That means the demand side is aware and the supply side — being deliberately readable — is still mostly unclaimed. |

### Direction 4 — Product-level verification for agent output

|  |  |
| --- | --- |
| **What** | Not code review. Given a preview deployment, verify the *product*: does the new user flow complete, does the page look right, does the API return what the spec says, does it work on the second platform. Hoplite’s thesis says this is where the review time goes; the tooling is thin. |
| **Stack** | Playwright for flows · visual diffing against a golden set · ephemeral preview environments (Modal, Fly Machines, or Namespace) · a vision model for “does this look broken” as a cheap first pass · report back into the PR |
| **Cost & timeline** | 6–10 weeks — the honest one on this list. $10–30/customer/month in compute. Price $30–80/developer/month; teams running many concurrent agents will pay more because the alternative is human minutes. |
| **Why now** | Every cloud-agent platform launching right now creates the same demand and none of them want to own the verification layer. Adjacent, not competing. |

### Direction 5 — Vendor-concentration audit as a small paid service

|  |  |
| --- | --- |
| **What** | Genuinely unglamorous, genuinely sellable. Map a small company’s single points of failure — CI, model provider, payments, auth, hosting, distribution channel — and deliver a switching-cost estimate and a tested fallback for the top three. Productize it later as a monitoring dashboard. |
| **Stack** | Start as a consulting deliverable with a repeatable template. Automate later: status-page polling, dependency graph from CI config, a monthly report. |
| **Cost & timeline** | You can sell the first one this week. $1,500–5,000 per engagement; $49–149/month once it’s a dashboard. |
| **Why now** | Yesterday created the urgency and Microsoft’s own 70%-on-OpenAI concentration makes the pitch land. Urgency decays in about two weeks — that’s the window. |

## Risk Factors

- **Self-hosting your runners is not the insurance you think it is.** Self-hosted runners were affected in this incident because the job-assignment control plane failed upstream of them. Real resilience means a second orchestrator, not just a second machine.
- **Log-based analytics is reactive by construction.** You learn about the scraper wave after your CPU spiked. If you build Direction 2, streaming and alerting are the product, not a v2 feature — otherwise you’ve shipped a nicer way to read yesterday’s bad news.
- **Blocking agent traffic can cut off future distribution.** Aggressive bot-blocking will also block the agents answering buyer questions about your category. Separate “expensive and useless” from “expensive and eventually a customer” before you write the firewall rule.
- **Do not fall in love with a harness.** Build one only if the harness *is* the product. Hoplite can justify a custom harness because their product is the execution environment. If you’re building a vertical app, a custom harness is a permanent maintenance tax on your smallest advantage.
- **Free tiers keep eating the shallow end.** Unlimited free ChatGPT text and a free Think button removes another layer of thin wrappers. If your value disappears when the model call is free, that’s your signal.

## Action Recommendations

**If you’re starting out**

- ✅ **Time your own outage today.** Assume Actions is unavailable for eight hours. Can you build and deploy? Write down the actual number of minutes. That number is your product spec if you build Direction 1, and your risk register if you don’t.
- ✅ **Read your access logs once this week.** Not analytics — raw logs. Compare the number to your GA4 dashboard. The gap is either a cost leak or a distribution channel you didn’t know you had.
- ✅ **Ship Direction 3 this week.** `llms.txt` plus a structured endpoint is a one-week job with near-zero cost and two simultaneous payoffs. Nothing else on this list has that ratio.
- ✅ **Don’t build a harness.** Unless the harness is the product, spend the hours on domain knowledge and data access instead.

**If you already ship**

- ✅ **Test the fallback, don’t just document it.** A mirrored remote you have never deployed from is not a fallback, it’s a hope. Run it once, on purpose, and record the elapsed time.
- ✅ **Decouple your agent loop from a single vendor’s control plane.** If agent execution, code review, and CI all live inside one provider, one incident stops all three. At minimum, keep the ability to run the verification step locally.
- ✅ **Instrument human vs. agent traffic before your next pricing or roadmap decision.** If bots are half your volume, half your conversion math is wrong in an unknown direction.
- ✅ **Put a routing layer in front of the model.** The #1 agentic model changed again this week. LiteLLM or OpenRouter takes an afternoon and turns a lock-in into a line item.

## What it means

Both of yesterday’s stories are the same failure: infrastructure built for a world that no longer exists.

CI/CD was designed around humans pushing a few times a day, and now absorbs agent-generated volume against a shared, capacity-limited queue — so a degradation becomes a nine-hour queue burn-down, and it takes your coding agent down with it. Web analytics was designed around a person in a browser, and now describes a minority of the requests hitting your server while a machine majority quietly runs up the bill.

Neither gets fixed by the incumbents soon. GitHub’s incentives point at Copilot surfaces, not at Actions reliability. Analytics vendors are structurally committed to the JavaScript beacon. That’s the gap, and it’s the ordinary kind — no frontier model, no funding, no team required. Log pipelines, fallback runners, `llms.txt`, preview verification. Unglamorous work on assumptions everyone else is still holding.

The builders who win the next quarter aren’t the ones with the best model access. They’re the ones who noticed which defaults stopped being true.
